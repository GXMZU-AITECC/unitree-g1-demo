## 仿真 vs 真机：两条路径一张图

```
仿真训练 (Isaac Sim)                    真机部署 (G1 Robot)
══════════════════════                  ═══════════════════

┌─────────────────────┐                 ┌─────────────────────┐
│ Isaac Sim 物理引擎    │                 │ 真实物理世界          │
│  (GPU 模拟 4096 个机器人) │              │  (重力、摩擦力、碰撞)  │
└─────────┬───────────┘                 └─────────┬───────────┘
          │                                       │
   仿真 IMU/电机状态                          真实 IMU/电机状态
   (PhysX 计算出来的)                      (传感器读到的真实数据)
          │                                       │
          ▼                                       ▼
   ┌─────────────┐                      ┌──────────────────┐
   │ 观察向量 obs │  ←── 一样 ──→        │ 观察向量 obs      │
   │ (480 维)     │                      │ (480 维)          │
   └──────┬──────┘                      └────────┬─────────┘
          │                                       │
    PyTorch 推理                          ONNX Runtime 推理
    (GPU, GPU上跑)                        (CPU, 机器人板载算力)
          │                                       │
          ▼                                       ▼
   ┌─────────────┐                      ┌──────────────────┐
   │ 动作 action  │  ←── 一样 ──→        │ 动作 action       │
   │ (29 维)      │                      │ (29 维)           │
   └──────┬──────┘                      └────────┬─────────┘
          │                                       │
   仿真 PD 控制器                          真机 PD 控制器
   (Isaac Sim 内置)                      (电机驱动板上的固件)
          │                                       │
          ▼                                       ▼
   关节扭矩 → 推动仿真关节               电机电流 → 推动真实关节
```

**关键点**：ONNX 模型在仿真和真机上跑的**输入输出完全一样**。仿真是靠 PhysX 模拟物理来获取 "传感器读数"，真机是真实 IMU 和电机编码器来获取传感器读数。

## 三大概念

### 1. ONNX — "模型格式化"

PyTorch 模型（`.pt`）只能在 Python+PyTorch 环境里跑。机器人上没有 PyTorch，也没有 GPU。

ONNX（Open Neural Network eXchange）是一个**通用格式**：
- 把 PyTorch 模型 "冻结" 成一个纯数学计算图
- ONNX Runtime（C++ 库）可以不依赖 PyTorch 直接加载推理
- 在 CPU 上跑 50Hz（每 0.02 秒一次）完全够快

```
model_N.pt (PyTorch)  ──torch.onnx.export()──▶  policy.onnx (ONNX)  ──ONNX Runtime──▶  推理结果
```

### 2. DDS — "机器人的神经系统"

DDS（Data Distribution Service）是机器人内部通信的总线。

```
┌──────────────────────────────────────────────────┐
│  机器人板载电脑                                     │
│                                                    │
│  g1_ctrl (我们的程序)                               │
│    │                                               │
│    │ 读取 (DDS Subscribe)                          │
│    ├──▶ lowstate: IMU数据 + 所有电机状态           │
│    │     (位置、速度、温度、力矩……)                  │
│    │                                               │
│    │ 写入 (DDS Publish)                            │
│    └──▶ lowcmd:   目标电机位置 + 刚度/阻尼参数     │
│                                                    │
│  ↑↓ DDS 网络                                        │
│                                                      │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐     │
│  │ 腿部电机1 │    │ 腿部电机2 │    │ 腰部电机  │ ... │
│  └──────────┘    └──────────┘    └──────────┘     │
└──────────────────────────────────────────────────┘
```

- `lowstate` = 机器人的 "感觉"（传感器数据）
- `lowcmd` = 我们的 "指令"（目标电机位置）
- DDS 在 1kHz 下交换这些数据，我们每 0.02 秒（50Hz）读一次、推理一次、写一次

### 3. FSM（有限状态机）— "机器人的行为切换"

机器人不能直接 "开始走路"。需要先初始化→站立→再走路。这是一个**有限状态机**：

```
           ┌──────────┐
           │ Passive   │  电机不加力，机器人是软的（断电状态）
           │ (id=1)    │
           └─────┬─────┘
                 │ L2 + ↑ (手柄按下)
                 ▼
           ┌──────────┐
           │ FixStand  │  电机加力，保持站立姿势
           │ (id=2)    │
           └─────┬─────┘
                 │ R1 + X (手柄按下)
                 ▼
           ┌──────────┐
           │ Velocity  │  ONNX 模型接管控制，开始速度跟踪
           │ (id=3)    │  ← 左摇杆控制前进/后退/转向
           └─────┬─────┘
                 │ L2 + B (手柄按下) → 回 Passive
                 ▼
           ┌──────────┐
           │ Passive   │  紧急停止！
           └──────────┘
```

- **任何时候按下 L2+B** 机器人会回到 Passive（软掉/倒地）——这是紧急停止按钮。
- **Velocity 状态下**左摇杆控制前进后退，左摇杆左右控制转向。
- `bad_orientation` 自动检测：如果机器人倒得太厉害，自动切回 Passive 防止进一步损坏。

## 50Hz 控制循环详解

```
时间线 (每次 0.02s)：
──────────────────── 循环开始 ────────────────────

1. 读取传感器 (update)
   ├─ IMU 陀螺仪 → base_ang_vel (3维)
   ├─ IMU 四元数 → projected_gravity (3维)
   ├─ 摇杆输入   → velocity_commands (3维)
   └─ 电机编码器  → joint_pos (29维) + joint_vel (29维)

2. 构建观察向量 (compute_observations)
   ├─ 6 个观察项，每个有 history_length=5
   ├─ 拼接成 [1, 480] 的向量
   └─ 按 deploy.yaml 中的 scale 缩放

3. ONNX 推理 (ort_session->Run)
   ├─ 输入: [1, 480] float 向量
   └─ 输出: [1, 29] float 向量（目标关节位置偏移量）

4. 处理动作 (process_actions)
   ├─ 加 offset (默认关节位置)
   ├─ 乘 scale (0.25)
   └─ clip (限制范围)

5. 发送指令 (write to lowcmd)
   ├─ 通过 joint_ids_map 映射到电机索引
   └─ 设置 q (目标位置) + kp (刚度) + kd (阻尼)

──────────────────── 循环结束 ────────────────────
```

## 观察向量的组成（480 维怎么来的？）

| # | 观察项 | 每步维度 | history_length | 总维度 |
|---|--------|----------|----------------|--------|
| 1 | `base_ang_vel` | 3 | 5 | 15 |
| 2 | `projected_gravity` | 3 | 5 | 15 |
| 3 | `velocity_commands` | 3 | 5 | 15 |
| 4 | `joint_pos_rel` | 29 | 5 | 145 |
| 5 | `joint_vel_rel` | 29 | 5 | 145 |
| 6 | `last_action` | 29 | 5 | 145 |
| **合计** | | **96** | | **480** |

`history_length=5` 意味着网络的输入不只是 "当前这一刻" 的传感器数据，而是**过去 5 个时刻**的数据叠在一起。这让模型能 "感知" 运动的趋势和变化率——比如从位置的变化推算出速度，从速度的变化推算出加速度。

模型用这个 480 维的输入，输出 29 个目标关节位置。

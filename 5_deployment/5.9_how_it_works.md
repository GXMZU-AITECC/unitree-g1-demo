# 5.9 源码深度解读

> 目标：逐行理解 C++ 控制器是怎么跑起来的。适合对代码好奇、想自己改的同学。

这一章我们按**启动→初始化→循环→推理**的顺序，走读整个控制器。

## 概览：6 个关键文件

| 文件 | 角色 | 300字概括 |
|------|------|----------|
| `main.cpp` | 入口 | 初始化 DDS，打印欢迎信息，启动 FSM，进入死循环 |

## main.cpp — 一切从这里开始

```cpp
#include "FSM/CtrlFSM.h"
#include "FSM/State_Passive.h"
#include "FSM/State_FixStand.h"
#include "FSM/State_RLBase.h"
#include "State_Mimic.h"
```

包含了 FSM 框架的全部状态类。`State_Mimic.h` 只在本文件 include，我们的 `config.yaml` 已经禁用了 Mimic 的注册，所以它不会被实例化。

```cpp
std::unique_ptr<LowCmd_t> FSMState::lowcmd = nullptr;
std::shared_ptr<LowState_t> FSMState::lowstate = nullptr;
std::shared_ptr<Keyboard> FSMState::keyboard = std::make_shared<Keyboard>();
```

**三个全局单例**，是所有状态共享的通信通道：
- `lowcmd` = 我们发给电机的命令（DDS Publisher）
- `lowstate` = 电机发给我们的状态（DDS Subscriber）
- `keyboard` = 手柄输入读取器

```cpp
void init_fsm_state()
{
    auto lowcmd_sub = std::make_shared<unitree::robot::g1::subscription::LowCmd>();
    usleep(0.2 * 1e6);
    if(!lowcmd_sub->isTimeout())
    {
        spdlog::critical("The other process is using the lowcmd channel, please close it first.");
        unitree::robot::go2::shutdown();
    }
    FSMState::lowcmd = std::make_unique<LowCmd_t>();
    FSMState::lowstate = std::make_shared<LowState_t>();
    spdlog::info("Waiting for connection to robot...");
    FSMState::lowstate->wait_for_connection();
    spdlog::info("Connected to robot.");
}
```

**看这里**：`init_fsm_state()` 做的事：
1. 订阅 lowcmd 通道（用 timeout 检测是否被其他进程占用）
2. 如果通道已被占用 → 报错、尝试关闭旧进程
3. 创建 `lowcmd` 和 `lowstate` 对象
4. **阻塞等待**直到收到机器人的第一个状态包 → 这不是忙等，是 DDS 的 subscriber 等待

```cpp
int main(int argc, char** argv)
{
    auto vm = param::helper(argc, argv);    // ① 解析参数 + 加载配置

    unitree::robot::ChannelFactory::Instance()->Init(0, vm["network"].as<std::string>());
    // ② 初始化 DDS 通道工厂，指定网络接口

    init_fsm_state();                        // ③ 连接机器人

    FSMState::lowcmd->msg_.mode_machine() = 5; // 29dof
    if(!FSMState::lowcmd->check_mode_machine(FSMState::lowstate)) {
        spdlog::critical("Unmatched robot type.");
        exit(-1);
    }
    // ④ 检查机器人类型是否匹配

    auto fsm = std::make_unique<CtrlFSM>(param::config["FSM"]);
    fsm->start();                            // ⑤ 启动状态机
    // CtrlFSM 的构造函数里会注册 config.yaml 中 _: 下列出的所有状态
    // start() 会进入 Passive 状态，然后开启一个后台线程跑主循环

    while (true) { sleep(1); }               // ⑥ 死循环保持进程存活
    return 0;
}
```

**关键注释**：
- ⑤ `CtrlFSM` 构造函数会遍历 `config["FSM"]["_"]` 中列出的所有状态，用 `REGISTER_FSM` 宏注册
- 因为我们的 `config.yaml` 注释掉了 Mimic 状态，所以只有 Passive、FixStand、Velocity 被注册
- ⑥ 主线程什么都不做，状态机在**另一个线程**里跑控制循环

## param.h — "自动发现策略目录" 的逻辑

这是最容易搞错的配置加载部分。

```cpp
inline std::filesystem::path get_bin_path() {
    std::vector<char> path(1024);
    ssize_t len = readlink("/proc/self/exe", &path[0], path.size());
    path[len] = '\0';
    return std::filesystem::path(&path[0]);
}
```

**用 `/proc/self/exe` 找到二进制文件的绝对路径**。所以不管你从哪个目录运行 `./build/g1_ctrl`，它都能找到自己的位置。

```cpp
inline void load_config_file()
{
    // 如果二进制在 bin/ 或 build/ 下 → 工程目录 = 叔叔目录 (../../)
    if(bin_path.parent_path().filename() == "bin" || bin_path.parent_path().filename() == "build")
    {
        proj_dir = bin_path.parent_path().parent_path();
        config_dir = proj_dir / "config";
    }
    else
    {
        proj_dir = bin_path.parent_path();
        config_dir = proj_dir;
    }
    config = YAML::LoadFile((config_dir / "config.yaml").string());
}
```

**路径推断规则**：
- `g1_ctrl` 在 `build/` 下 → `proj_dir = g1_29dof/` → `config/` 就在 `g1_29dof/config/`
- `g1_ctrl` 直接在 `g1_29dof/` 下 → `proj_dir = g1_29dof/` → 同上

```cpp
inline std::filesystem::path parser_policy_dir(std::filesystem::path policy_dir)
{
    // 相对路径 → 基于 proj_dir 转绝对路径
    if (policy_dir.is_relative()) {
        policy_dir = param::proj_dir / policy_dir;
    }

    // 如果这个目录下没有 exported/ 子目录 → 扫描子目录
    if (!std::filesystem::exists(policy_dir / "exported")) {
        auto dirs = std::filesystem::directory_iterator(policy_dir);
        // 收集所有子目录
        // 按名称排序
        // 从最后一个开始向前找含有 exported/ 的目录
    }
    return policy_dir;
}
```

**自动发现逻辑**：如果 `config/policy/velocity/` 下没有 `exported/`，它会扫描子目录（`v0/`, `v1/` 等），找到最新的含有 `exported/` 的版本。这样你可以同时保留多个版本的策略，控制器自动选最新的。

## unitree_articulation.h — 传感器→观察向量

```cpp
void update() override
{
    std::lock_guard<std::mutex> lock(lowstate->mutex_);
    
    // ① 角速度：直接读 IMU 陀螺仪
    for(int i(0); i<3; i++) {
        data.root_ang_vel_b[i] = lowstate->msg_.imu_state().gyroscope()[i];
    }
    
    // ② 姿态 → projected_gravity
    data.root_quat_w = Eigen::Quaternionf(
        lowstate->msg_.imu_state().quaternion()[0], // w
        lowstate->msg_.imu_state().quaternion()[1], // x
        lowstate->msg_.imu_state().quaternion()[2], // y
        lowstate->msg_.imu_state().quaternion()[3]  // z
    );
    data.projected_gravity_b = data.root_quat_w.conjugate() * data.GRAVITY_VEC_W;
    // GRAVITY_VEC_W = (0, 0, -1)  →  世界坐标系中的重力方向
    // quat.conjugate() * gravity_vec  →  把世界重力转到机器人坐标系
    // 结果 (gx, gy, gz)_body 就是机器人 "感觉" 到的重力方向
    
    // ③ 关节位置和速度：从电机编码器读
    for(int i(0); i< data.joint_ids_map.size(); i++) {
        data.joint_pos[i] = lowstate->msg_.motor_state()[data.joint_ids_map[i]].q();
        data.joint_vel[i] = lowstate->msg_.motor_state()[data.joint_ids_map[i]].dq();
    }
}
```

**`projected_gravity` 怎么算的？**

重力在世界坐标系中永远是 `(0, 0, -1)`（垂直向下）。把机器人的当前姿态的四元数取共轭，就是 "把世界坐标系的向量转到机器人坐标系" 的旋转。结果就是 "在我身体的坐标系里，重力在哪个方向"——比如机器人前倾时，`projected_gravity.x` 会变正（重力 "拉" 向身体前方）。

**`joint_ids_map` 做了什么？**

仿真中关节的顺序：[left_hip_yaw, left_hip_roll, left_hip_pitch, ..., right_ankle_pitch]
SDK 电机索引：[0, 1, 2, 3, ..., 28]
但它们的对应关系不是 0→0, 1→1...

`joint_ids_map` = `[0, 6, 12, 1, 7, 13, ...]` 意味着：
- 仿真关节 0 (left_hip_yaw) → 电机索引 0
- 仿真关节 1 (left_hip_roll) → 电机索引 6
- 仿真关节 2 (left_hip_pitch) → 电机索引 12
- ……

这样 `joint_pos[0]` 存的总是 "仿真关节0" 的值，不管它对应的是哪个电机。

## algorithms.h — ONNX Runtime 推理

```cpp
OrtRunner(std::string model_path)
{
    env = Ort::Env(ORT_LOGGING_LEVEL_WARNING, "onnx_model");
    session_options.SetGraphOptimizationLevel(ORT_ENABLE_EXTENDED);
    
    session = std::make_unique<Ort::Session>(env, model_path.c_str(), session_options);
    // 加载 ONNX 模型文件
    
    // 读取输入信息（名称、形状、大小）
    for (size_t i = 0; i < session->GetInputCount(); ++i) {
        Ort::TypeInfo input_type = session->GetInputTypeInfo(i);
        input_shapes.push_back(input_type.GetTensorTypeAndShapeInfo().GetShape());
        auto input_name = session->GetInputNameAllocated(i, allocator);
        input_names.push_back(input_name.release());
    }
    // 对输入大小为 shape[1]×shape[2]×... 预计算总大小
    for (const auto& shape : input_shapes) {
        size_t size = 1;
        for (const auto& dim : shape) { size *= dim; }
        input_sizes.push_back(size);
    }
    
    // 读取输出形状 → 预分配 action 向量
    Ort::TypeInfo output_type = session->GetOutputTypeInfo(0);
    output_shape = output_type.GetTensorTypeAndShapeInfo().GetShape();
    action.resize(output_shape[1]);
}
```

**每次推理**：
```cpp
std::vector<float> act(std::unordered_map<std::string, std::vector<float>> obs)
{
    auto memory_info = Ort::MemoryInfo::CreateCpu(OrtDeviceAllocator, OrtMemTypeCPU);
    
    // 检查所有需要的输入都在 obs 字典中
    for (const auto& name : input_names) {
        if (obs.find(name) == obs.end()) {
            throw std::runtime_error("Input name " + std::string(name) + " not found");
        }
    }
    
    // 构建输入张量
    std::vector<Ort::Value> input_tensors;
    for(int i(0); i<input_names.size(); ++i) {
        auto& input_data = obs.at(std::string(input_names[i]));
        auto input_tensor = Ort::Value::CreateTensor<float>(
            memory_info, input_data.data(), input_sizes[i],
            input_shapes[i].data(), input_shapes[i].size());
        input_tensors.push_back(std::move(input_tensor));
    }
    
    // 推理！
    auto output_tensor = session->Run(Ort::RunOptions{nullptr},
        input_names.data(), input_tensors.data(), input_tensors.size(),
        output_names.data(), 1);
    
    // 复制输出到 action 向量
    auto floatarr = output_tensor.front().GetTensorMutableData<float>();
    std::lock_guard<std::mutex> lock(act_mtx_);
    std::memcpy(action.data(), floatarr, output_shape[1] * sizeof(float));
    return action;
}
```

**线程安全**：`act_mtx_` 保护 `action` 向量。推理在后台线程调用 `act()`，主线程调用 `get_action()` 读取最新结果。

## State_RLBase.cpp — RL 策略状态

```cpp
State_RLBase::State_RLBase(int state_mode, std::string state_string)
: FSMState(state_mode, state_string) 
{
    auto cfg = param::config["FSM"][state_string];
    auto policy_dir = param::parser_policy_dir(cfg["policy_dir"].as<std::string>());
    
    // ① 创建 RL 环境
    env = std::make_unique<isaaclab::ManagerBasedRLEnv>(
        YAML::LoadFile(policy_dir / "params" / "deploy.yaml"),
        std::make_shared<unitree::BaseArticulation<LowState_t::SharedPtr>>(FSMState::lowstate)
    );
    // ManagerBasedRLEnv 的构造函数会解析 deploy.yaml
    // 初始化 ObservationManager（6个观察项，history buffer）
    // 初始化 ActionManager（JointPositionAction）
    
    // ② 创建 ONNX 推理器
    env->alg = std::make_unique<isaaclab::OrtRunner>(policy_dir / "exported" / "policy.onnx");
    
    // ③ 注册安全检查：如果姿态歪了→自动切回 Passive
    this->registered_checks.emplace_back(
        std::make_pair(
            [&]()->bool{ return isaaclab::mdp::bad_orientation(env.get(), 1.0); },
            FSMStringMap.right.at("Passive")
        )
    );
}
```

**`env->step()` — 每个控制周期的核心**：
```cpp
void State_RLBase::run()
{
    // env->step() 在 base class 的 run() 里已经调用过了
    // 拿到处理后的动作（scale+offset 都应用完了）
    auto action = env->action_manager->processed_actions();
    
    // 通过 joint_ids_map 将 29 个动作值映射到对应的电机索引
    for(int i(0); i < env->robot->data.joint_ids_map.size(); i++) {
        lowcmd->msg_.motor_cmd()[env->robot->data.joint_ids_map[i]].q() = action[i];
    }
    // q = target position → DDS publish → 电机的 PD 控制器执行
}
```

## 完整调用链路（50Hz）

```
CtrlFSM::run() [后台线程，50Hz]
  │
  ├─ FSMState::run_check()        ──▶ 检查 registered_checks
  │     └─ bad_orientation? → 切到 Passive
  │
  └─ current_state->run()
        │
        └─ State_RLBase::run()    ──▶ 实际执行控制逻辑
              │
              └─ 在此之前，FSMState 的基类已经调用了：
                    env->robot->update()         ──▶ 读传感器
                    env->compute_observations()  ──▶ 构建 480 维 obs
                    env->alg->act(obs)           ──▶ ONNX 推理
                    env->process_actions()       ──▶ scale+offset
                    
              └─ 然后 State_RLBase::run() 只是：
                    把 action[i] 写到 lowcmd->motor_cmd()[joint_ids_map[i]].q()
```

**注意**：实际的控制循环在 `CtrlFSM.h` 的后台线程里，不在 `State_RLBase.cpp` 的可视范围内。`State_RLBase::run()` 只负责 "把推理结果写进电机命令" 这一小段。
